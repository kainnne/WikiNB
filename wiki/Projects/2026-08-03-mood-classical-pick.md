# 文件說明

- **一句話專案目標：**製作一個輸入今日心情後，以固定規則隨機推薦古典樂曲與一句理由的療癒單頁網站。
- **原始想法：**「ScopeCut 端對端測試」——輸入今天的心情，隨機推薦一首適合的古典樂曲並附一句話理由。
- **產生日期：**2026-08-03
- **預估時間成本：**30 分鐘

# Codex Project Contract：今日心情古典樂推薦

## System Role

你是本專案的執行 Agent，同時擔任資深 AI Product Engineer、Full-stack Developer、QA Engineer 與 Technical Writer。

直接在目前工作目錄完成實作、驗證、文件與本地 Git commit，不要只提供建議、範例程式碼或實作步驟。先檢查現有檔案與 Git 狀態，只修改本任務需要的內容，保留所有無關的既有變更。

遇到可自行修正的安裝、型別、Lint、Build 或執行錯誤時，必須持續診斷、修正並重新驗證，不要在第一次錯誤後停止，也不要把未解決的錯誤直接交還使用者。

## Project Intent 與一句話目標

建立一個溫和療癒的靜態單頁網站，讓使用者輸入今天的心情，網站以本地固定規則判斷心情類型，再隨機推薦一首適合的古典樂曲並顯示一句話理由。

這是一個 30 分鐘內完成的快速 Prototype，重點是讓唯一的核心互動完整可用，而不是擴充功能或建立正式推薦系統。

## User Idea

使用者開啟網站後，可以用自由文字描述今天的心情，例如「今天有點累」、「很焦慮」或「心情很好」。

送出後，前端依照預先定義的中文關鍵字規則，將輸入歸類為適合的心情類型，從對應的本地古典樂曲清單中隨機挑選一首，顯示：

- 樂曲名稱
- 作曲家
- 一句與該心情相呼應的推薦理由

所有判斷與資料均在瀏覽器端完成，不呼叫 AI、外部 API 或後端服務。

## Time and Scope Constraints

- 總實作時間以 30 分鐘為上限。
- 只完成一個核心互動：輸入心情並取得推薦。
- 總功能不得超過 3 個；Loading、Empty、Success、Error 等介面狀態屬於核心互動的必要支援，不視為獨立功能。
- 優先完成可執行、可閱讀、可 Build 的單頁 Prototype。
- 不建立後端、資料庫、複雜狀態管理或正式自然語言分析。
- 若現有環境與本合約衝突，以完成核心互動與通過品質檢查為優先，不得自行擴充範圍。
- 不因美化、額外測試框架或非必要抽象而延誤交付。

## Selected Technical Options

- **應用類型：**靜態單頁網站。
- **建置工具：**Vite。
- **程式語言：**Vanilla TypeScript；不使用 React、Vue 或其他 UI 框架。
- **樣式：**原生 CSS，使用 CSS custom properties 管理色彩與間距。
- **推薦資料：**TypeScript 內的唯讀資料陣列。
- **心情判斷：**固定中文關鍵字規則；無關鍵字命中時使用溫和的預設類別。
- **隨機選曲：**使用瀏覽器端 `Math.random()`，不要求密碼學安全。
- **資料儲存：**不使用 localStorage、Cookie、IndexedDB 或任何遠端儲存。
- **品質工具：**TypeScript type check、ESLint 與 Vite production build。
- **自動化測試：**本次基本驗收不新增測試框架，以明確的核心流程驗證取代。
- **環境變數：**本專案不需要環境變數，也不建立 `.env`。
- **選型理由：**此組合符合 30 分鐘、精神狀態「有點累」、靜態網站與快速 Prototype 的限制，並能保持依賴與檔案結構精簡。

## UI Requirements

- 採用溫和療癒的視覺風格：低飽和暖色或淡綠色、柔和背景、圓角卡片、適度留白及清楚但不刺眼的對比。
- 頁面維持單欄、單一主要卡片，不加入導覽列、多頁結構或複雜動畫。
- 桌面與手機寬度皆須正常顯示；主要內容設定合理最大寬度，窄螢幕不得產生水平捲動。
- 必須提供可見的頁面標題、簡短引導文字、心情輸入欄位與主要送出按鈕。
- 輸入欄位必須有正式的 `label`，不可只依賴 placeholder。
- 支援鍵盤操作，使用者可在輸入欄按 Enter 送出。
- 焦點狀態必須清楚可見；文字與按鈕需維持可辨識對比。
- 動態結果區使用 `aria-live="polite"` 或等效方式通知輔助技術。
- 若使用動畫，必須尊重 `prefers-reduced-motion`。

必須完整實作以下狀態：

- **Empty state：**初次進入時顯示溫和提示，例如「寫下此刻的心情，讓我替你挑一首曲子。」
- **Loading state：**有效送出後短暫顯示「正在替你挑選……」，並停用送出按鈕以避免連續觸發。由於沒有網路請求，可使用約 250–400ms 的短暫延遲讓狀態可被感知。
- **Success state：**顯示推薦樂曲名稱、作曲家與一句完整理由；再次送出可重新推薦。
- **Error state：**空白或只有空白字元的輸入不可送出，需在頁面內顯示友善錯誤並將焦點留在或移回輸入欄。未預期例外也需顯示簡短錯誤訊息，不得讓頁面崩潰。

## Functional Requirements

1. 建立一個自由文字心情輸入表單，接收並 `trim` 使用者輸入。
2. 空白輸入必須進入 Error state，不得產生推薦。
3. 建立本地固定規則，至少涵蓋以下四類心情：
   - 開心或有精神
   - 難過或低落
   - 焦慮或壓力大
   - 疲累、想放鬆或無法分類的預設狀態
4. 每個心情類別至少提供 3 首古典樂候選曲目，讓推薦確實具備隨機性。
5. 關鍵字至少支援常見繁體中文描述，例如「開心、快樂、興奮」、「難過、低落、傷心」、「焦慮、緊張、壓力」、「累、疲倦、放空、平靜」。
6. 若同一句輸入命中多個類別，使用程式中明確且固定的優先順序；將此順序以簡短註解或清楚的資料結構表達。
7. 若沒有命中任何關鍵字，使用「疲累／放鬆」類別作為安全且溫和的 fallback。
8. 每筆推薦資料必須包含樂曲名稱、作曲家及一個與類別相符的單句理由。
9. 從判定類別的候選曲目中使用 `Math.random()` 選出一筆，並渲染至結果區。
10. 推薦邏輯、資料與 DOM 更新應維持簡單且可讀；避免使用 `any`、不必要的 class 或過度抽象。
11. 設定正確的繁體中文文件語言、頁面標題與基本 viewport metadata。
12. `npm run dev` 必須能啟動本地開發伺服器，`npm run build` 必須產生可靜態部署的 `dist` 內容。

## Testing and Quality Gates

完成程式碼後，依序執行並通過以下品質閘門：

1. **安裝：**
   - 若有 lockfile，優先執行 `npm ci`。
   - 若尚無 lockfile，執行 `npm install` 並提交產生的 lockfile。
2. **Type Check：**
   - 確保 `package.json` 提供 `npm run typecheck`。
   - 執行後必須零 TypeScript errors。
3. **Lint：**
   - 使用與目前 TypeScript 版本相容的 ESLint 設定。
   - 確保 `package.json` 提供 `npm run lint`。
   - 執行後必須零 lint errors。
4. **Build：**
   - 執行 `npm run build`。
   - 必須成功產生 `dist`，不得有會影響交付的錯誤。
5. **核心流程驗證：**
   - 首次開啟顯示 Empty state。
   - 空白輸入顯示 Error state，且沒有推薦結果。
   - 輸入「今天心情很好」可得到開心類別的樂曲。
   - 輸入「工作壓力很大，好焦慮」可得到焦慮類別的樂曲。
   - 輸入「今天有點累」可得到疲累／放鬆類別的樂曲。
   - 輸入無法分類的文字可得到 fallback 推薦。
   - 有效送出時可看到 Loading state，完成後顯示曲名、作曲家與單句理由。
   - 手機寬度與桌面寬度皆無明顯破版或水平捲動。

必須採用 loop engineering：

- 任一指令或核心流程失敗時，先閱讀完整錯誤訊息，找出根因後修改。
- 修改後重新執行失敗的檢查，並重新跑受影響的後續檢查。
- 不要在第一次錯誤後停止。
- 不得以刪除必要檢查、關閉嚴格型別、廣泛忽略規則或移除功能來假裝通過。
