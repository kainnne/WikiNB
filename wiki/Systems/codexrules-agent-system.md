# CodexRules 與 agents CLI 規則系統

CodexRules 是私人工作規則的中央來源，`agents` CLI 則負責把這套規則安裝或更新到不同專案。Codex 與 Claude Code 共用這份來源，目標是讓 Agent 一進入專案就知道基本工作方式，又不必每次載入所有長篇說明。

## 分層方式

- 根目錄 `AGENTS.md`：只放高頻原則與「什麼任務該讀哪份規則」的路由。
- `AGENTS_Intro/`：依工作類型拆分詳細規則，需要時才讀。
- 專案自己的 `AGENTS.md`：補充該 repository 的命令、限制與驗收方式。
- README／HANDOFF／STATUS：保存專案事實與目前狀態，不塞進通用規則。

公開 repository 還要區分可公開的入口與本機私人規則。入口只保留必要導向，私人背景與路徑留在未追蹤的本機文件。不能因為 Agent 需要讀，就把整份私人規則放進 Git。

## Claude 與 Codex 讀同一份規則

目前中央來源採用的方式是讓 `CLAUDE.md` 導向共同的 `AGENTS.md` 與按需文件。Claude 的入口負責帶路，不另外維護一套內容相似的長篇規則。

兩個入口若各寫一份完整規範，更新時很容易只改到其中一份。久了就會出現一邊允許發布、另一邊仍說先交草稿，或一邊知道新路徑、另一邊繼續找舊專案。共同來源讓差異比較容易被看見，也讓修正有明確位置。

但共用來源不等於每個專案都已同步。CLI 本身、中央規則與專案已安裝的規則可能是不同版本；要查目前狀態，應核對實際入口和診斷結果，不能只看 CLI 顯示的版本。本篇更新的是方法紀錄，沒有代替各專案執行規則升級。

## `agents` CLI 的用途

新專案可用 `agents install` 安裝中央規則；中央規則更新後，用 `agents update` 同步受管理區塊。CLI 會保留專案自己寫的非管理內容，也能自動包含中央規則資料夾中新加入的 Markdown 文件。

## Token 效率原則

規則檔應告訴 Agent 如何找到答案，而不是複製每個專案的完整背景。開始任務時先讀短入口、專案狀態與相關來源；只有跨專案整理或知識同步時才擴大範圍。這樣能減少重複掃描，也比較不會讓過期資訊長期佔據上下文。

## 分工依任務決定，交接保留判斷空間

有些工作適合一路做到實作、測試與交付，有些研究、教案或創作需要使用者持續介入。可以依工具能力與當次需求分工，不必把某個 Agent 永久指定成企劃，另一個永遠只照單寫程式。

交接要讓接手者知道目標和證據，也允許它發現前一步的假設不成立。比較有用的內容包括：

- 這次要完成什麼，以及使用者已決定哪些事。
- 可以修改的範圍、必須保留的內容，以及既有變更。
- 已完成什麼、怎麼驗證、還有哪些限制。
- 哪份程式或文件是事實來源，以及資料日期與適用版本。
- 下一步真正卡在哪裡，哪些只是建議而非已批准的需求。

例如，交接「把嵌入編輯器接好」仍太模糊。應指出現有 SDK、宿主儲存 callback、已測過的流程，並明說後台寫入是否完成。接手者先核對當前程式與 Git 狀態，再決定怎麼補；不能把上一個 Agent 的完成摘要當作唯一證據。

已存在 HANDOFF 或 STATUS 時，更新原來相應段落，避免到處新增相互競爭的狀態文件。一次性除錯輸出不必全部留下，能讓下一位重現問題的步驟與限制才值得保存。

## 規則需要標出適用範圍

使用者偏好常從具體作品形成。某頁不需要灰色補充小字，不代表教學文章也不能解釋；某次聲音處理很好聽，也不代表所有品牌都固定用同一組參數。

把偏好整理成規則時，應留下它處理的問題、適用情境與最新決策。專案事實留在專案；跨不同工作仍成立、能重複使用的方法，才提升成共同規則。遇到衝突時先看本輪指示和較接近目標的規範，不把舊案例當永久命令。

這也影響自主性：使用者已授權的工作，應把必要實作與驗證接著做完；只有缺少必要資訊，或選擇會改變權利、公開範圍、成本與難以回復的結果時，才需要澄清。共同規則應幫忙完成工作，而不是製造重複確認。

## 系統層操作的熔斷規則

專案內的程式修改、測試與可回復工作仍讓 Agent 自主完成；只有操作範圍進入主力機的登入環境、系統服務、預設 handler、Finder／圖示快取或其他全域設定時，才提升安全門檻。

這類工作採「盤點、備份、單一變更、真實驗證、再決定下一步」的交易式流程。若服務或命令阻塞、留下未知程序，或 Finder 與背景 App 開始異常，Agent 必須停止同一子系統的寫入與替代工具重試，改為保存證據、唯讀診斷並等待決策。完整方法見 [[Systems/safe-system-operations-with-agents]]。

## 排程設計與歷史狀態

這套系統曾把來源監測、晨間摘要、GEO 稽核與發布決策拆成不同排程，並限制監測工作只能讀取資料、不能自行修改或上架。這項設計的價值是把「發現變化」「判斷重要性」與「正式發布」分開，讓 Agent 的權限和責任更容易檢查。

2026-09-03 的紀錄是當時所有自動排程已暫停，WikiNB、GEO 與跨專案整理由 Kaine 明確觸發。這是階段狀態，不應拿來推斷今天所有排程仍然停用；目前狀態須回到實際排程設定確認。方法上仍要區分監測、整理與發布的授權，不能因為允許觀察，就自行公開內容。
