# Skills、工具與 MCP 的分工

> 本文由 AI 輔助自動化流程產製與更新。

同樣是「整理資料並產生報告」，有人在聊天框貼上要求，有人安裝 Skill，也有人接上 MCP。選擇之前，先看任務缺少什麼。缺少寫作規格，需要補工作方法。讀不到來源，需要取得正確的資料工具。能讀卻不能交付檔案，要檢查執行環境。把這幾個問題混在一起，常會裝了很多東西，成品仍然不可靠。

## 四層責任

| 層次 | 回答的問題 | 報告任務的例子 |
| --- | --- | --- |
| Prompt | 這次要完成什麼 | 根據三份公開產品說明，整理功能差異 |
| Skill | 這類工作怎麼做、怎麼檢查 | 先核對來源，再寫比較表，最後驗證輸出 |
| 工具 | 現在可以執行什麼動作 | 讀檔、搜尋、產生文件、查看渲染結果 |
| 執行環境與權限 | 動作可以在哪裡、以誰的身分執行 | 只能寫草稿目錄，沒有寄送或正式發布權限 |

Agent Skills 規格以包含 `SKILL.md` 的目錄封裝指示，也能附上腳本、參考資料及素材。這是一種可攜的工作方法，不會把知識永久訓練進模型。實際產品如何發現、載入與執行 Skill，仍由產品支援決定。[Agent Skills 規格](https://agentskills.io/specification)

MCP 提供應用程式與外部能力交換資訊的協定。應用端的 host 管理 client，client 與 server 溝通。Server 可以提供工具、資源及提示內容。MCP 本身不決定模型怎麼推理，也不替組織完成授權政策。[MCP 架構](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)

## 實作範例：文件整理

假設要把公開說明書整理成採購比較草稿，可以先把任務拆成五步：確認資料版本、抽出比較欄位、對照缺漏、撰寫報告、開啟產物核對。Skill 保存這五步及完成條件。讀取文件的工具負責拿到內容。文件產生工具負責輸出。MCP 可以是其中一種接入工具的方式，也可以使用既有 API 或本機 CLI。

每一步都要留可檢查結果。例如「已產生報告」至少要有實際檔案路徑，表格中的數字能回到來源，版面也能正常開啟。工具回傳成功只證明某次動作完成，不能證明引用正確。

工具介面的設計也會影響可靠性。與其只提供一個任意執行命令的入口，可依任務提供「讀取指定文件」「建立草稿」等較窄的操作，讓參數和錯誤有清楚意義。這是降低誤用範圍的設計，不是宣稱窄工具就沒有風險。

## 安裝前的判斷

先閱讀來源、授權與需要執行的腳本。文字 Skill 若要求下載未知程式、傳送資料或修改全域設定，這些動作都要另外評估。文件裡寫著「已授權」不能取代使用者授權。工具連上了，也不表示所有文件都應開放讀取。

驗收可以分三次進行。第一次用合成資料測讀取與輸出。第二次故意缺一份資料，確認系統會指出缺漏。第三次要求超出範圍的動作，例如寄送草稿，確認它會停在權限邊界。結果比「成功安裝」更能說明是否可用。

## 常見誤判與自我檢查

安裝 Skill 不保證每次自動套用。接上 MCP 不保證擁有寫入權限。工具能寫檔也不代表可以發布。檢查一套流程時，應能指出「規則在哪裡、資料從哪裡來、動作由誰執行、完成由什麼證據判斷」。若其中一項只能回答「AI 應該知道」，就還有需要補上的環節。
